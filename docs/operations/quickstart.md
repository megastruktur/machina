# Operations — fresh-install quickstart (P12)

Runbook for one fresh MAI instance: decide the enrollment parameters, install
the controller host, and reach the first authenticated browser session.
Every command below exists in this tree and is verified against the real
surface by `tests/docs/test_docs_consistency.py`.

Anchors: `docs/architecture/auth-and-origin.md` (exposure/bootstrap),
`docs/architecture/host-supervision.md` (SSH lane),
`docs/architecture/contracts.md` C02/C04/C08/C09. Companion runbooks:
`recovery.md` (backup/restore), `uninstall.md` (rotation/teardown),
`acceptance.md` (what the end-to-end journeys prove).

## 0. Scope and honesty

- This covers the **single-host install**: the stack runs on the host you
  install, and that host is also the first managed server (the installer
  provisions the SSH lane it will be supervised through).
- The stack **publishes no ports** (`compose.yaml` has no `ports:`).
  Browser access requires an operator-supplied TLS reverse proxy —
  §6 below is configuration guidance, not a shipped component.
- The installer **never prints or sets a password**. The web admin
  credential is created exactly once by you (§7).

## 1. Prerequisites

On the target host (the machine MAI will run on and manage):

| Requirement | Notes |
|---|---|
| Linux x86_64, root shell | The installer provisions accounts, sudo, firewall — it refuses to run unprivileged (`MAI_INSTALL_SKIP_ROOT_CHECK=1` is the sandbox-test seam only) |
| Docker Engine + Compose v2 | `docker compose version` must work |
| `uv` on PATH **or** `backend/.venv` | The stable CLI seam is `uv run --frozen --project <repo>/backend python -m mai.cli`, falling back to `backend/.venv/bin/python -m mai.cli`; override with `MAI_INSTALL_CLI` |
| OpenSSH server running | Host key is fingerprinted (`ssh-keygen -lf`), never modified |
| This repository checked out | `--repo` defaults to the directory above `scripts/` |
| `ufw` or `firewalld` (optional) | Used only when present and active; otherwise the scoped rule is printed for manual application |

Python ≥ 3.14 is required by `backend/pyproject.toml`; `uv sync --frozen`
installs the locked interpreter packages from `backend/uv.lock` — no manual
Python install needed when `uv` is present.

## 2. Decide the enrollment parameters

| Parameter | How to choose |
|---|---|
| `--server-id` | One RFC-4122 UUID (`uuidgen`), generated by you; it is the permanent identity of this server |
| `--grant-scope` | `none` (no sudo), `narrow` (NOPASSWD for `systemctl start/stop/restart/status docker.service` only), `broad` (`NOPASSWD: ALL`, trusted-admin). The chosen scope is shown in the plan before anything is applied |
| `--controller-address` | IPv4/CIDR the SSH firewall rule is scoped to — the address your browser/admin lane and future SSH supervision come from. Blanket targets (`0.0.0.0/0`, `::/0`, `any`) and prefixes broader than /8 are **refused** |
| `--ssh-user` | Service account name (default `mai`; key-only login, no password is ever set) |
| `--ssh-port` | Port used in the firewall rule (default 22) |
| `--ssh-host` | Address written into the canonical profile (default `127.0.0.1`; set the address a REMOTE controller uses to reach this host) |
| `--data-root` | Controller data root for the canonical pair — explicit, never inferred (C02 rule 1). **Use the same path for `backup-restore.sh` and `uninstall-host.sh`.** |
| `--stack-profiles` | Comma list of `core,worker,search,memory` (default `core`; see §8) |

Create the controller SSH key on your admin machine and copy the **public**
key to the target (the installer authorizes exactly one key line):

```bash
ssh-keygen -t ed25519 -f ~/.ssh/mai_controller -N "" -C mai-controller
scp ~/.ssh/mai_controller.pub root@TARGET:/root/mai_controller.pub
```

### 2.1 Enrolling a server through the UI (guided) and its manual prerequisites

Every additional Linux server is enrolled in the browser: open **Enroll
server** in the left navigation drawer and follow the guided flow. The one
external step is authorizing the controller's public key on the target —
MAI never provisions users, groups, sudoers rules or firewall rules for you.

**Guided browser flow (in order):**

1. **Copy the public key** — the enrollment card shows the controller's
   PUBLIC key with a **Copy public key** button. The controller key is the
   installer-provisioned `MAI_SSH_KEY_MAI` resolver entry; there is no
   credential field in the browser, and nothing to type or paste from a
   shell. (Operators may point the server at a different installed key by
   setting `MAI_SSH_CREDENTIAL_REF` in the `mai-api`/worker environment —
   a reference NAME, never a secret value, and never a browser input.)
2. **Authorize it on the target** using your existing admin access: append
   the copied PUBLIC line to the target user's `authorized_keys` (`0700` on
   `.ssh`, `0600` on `authorized_keys`, owned by that user).
3. **Fill the SSH details** in the same card: display name, SSH host, port,
   user, and privilege mode — `sudo` requires noninteractive passwordless
   sudo for the operations you want MAI to perform, `root` requires the SSH
   user to actually be uid 0, `none` performs no elevation check.
4. **Test connection** — one guided action. It first scans the endpoint:
   discovery lists the host keys the target actually presents
   (trust-on-first-use candidate collection; this is NOT yet an
   authenticated connection). When exactly ONE host key is presented, the
   same action continues straight into the pinned test with it — no extra
   click. When several keys are presented, you must select one explicitly
   (the button then reads **Test selected host key**) before the pinned
   test runs. Compare the offered fingerprint(s) against one you obtained
   independently (e.g. `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`
   run on the target) whenever the host is not already independently
   trusted. The pinned test connects with that exact fingerprint pinned and
   reports the real Linux identity (hostname, OS, kernel) plus the
   privilege result; it is side-effect-free.
5. **Trust and enroll** — tick **Trust this host key**, complete the form,
   and press **Enroll server**. Enroll re-verifies the connection against
   the accepted fingerprint immediately before writing: a key that changed
   between test and enroll is refused (`host_key_mismatch`) and nothing is
   written; keys are never silently rotated. On success the canonical
   profile plus exactly ONE host-key pin are stored
   (`<data_root>/servers/<server_id>/known_hosts`), the new server is
   selected in the workspace, its profile panel shows the pinned host key
   read-only, and the pinned identity probe works immediately with no
   second trust step. A HOST key that changes later is refused on every
   connection — MAI never auto-rotates a host pin; accepting a new host
   fingerprint is an explicit admin re-enrollment of that server with the
   new fingerprint recorded. Rotating the CONTROLLER's own SSH key is a
   separate, supported operation (see `uninstall.md` Mode 1 — controller
   key only).

**Manual prerequisites on the target (still yours — nothing is
auto-provisioned):**

1. **Service account + `docker` group membership** (required so `docker ps -a` and `docker compose` over SSH can read `/var/run/docker.sock` without `permission_denied`):
   ```bash
   sudo useradd --create-home --shell /bin/bash --comment "mai-controller" mai
   sudo usermod -aG docker mai
   ```
2. **Controller public key in `/home/mai/.ssh/authorized_keys`** — the line
   copied from the enrollment card (step 2 above), with `0700` on `.ssh`,
   `0600` on `authorized_keys`, owned by `mai:mai`.
3. **Sudoers rule in `/etc/sudoers.d/90-mai-mai`** (`0440`, validated with `visudo -cf`) matching the privilege mode you will select:
   - `sudo` (narrow grant): `mai ALL=(root) NOPASSWD: /usr/bin/systemctl start docker.service, /usr/bin/systemctl stop docker.service, /usr/bin/systemctl restart docker.service, /usr/bin/systemctl status docker.service`
   - `root` (broad grant): `mai ALL=(ALL) NOPASSWD: ALL`
4. **Scoped SSH firewall rule**: allow TCP port `22` from the controller IP or from the `mai` Docker bridge subnet (e.g. `172.32.0.0/16` when `mai-api` connects to its own host via the bridge gateway `172.32.0.1`).

## 3. Plan first (read-only, exit 0)

```bash
sudo bash scripts/install-host.sh \
  --server-id "$(uuidgen)" \
  --data-root /var/lib/mai \
  --public-key /root/mai_controller.pub \
  --grant-scope narrow \
  --controller-address 192.168.1.10/32 \
  --stack-profiles core \
  --print-plan
```

`--print-plan` prints the exact plan (grant scope, firewall rule, steps) and
exits 0 **without applying anything**. Check the account, the sudoers line,
the rule scope and the stack description before continuing.

## 4. Apply

Re-run without `--print-plan` and with the SAME parameter values. A tty asks
for consent; scripts pass `--yes`. Idempotent and resume-safe: existing
accounts/keys/config are preserved; a grant-scope change is refused unless
you pass `--reconcile-grants` (which replaces only the installer-managed
sudoers file, never foreign ones).

Steps performed (all idempotent):

1. service account (key-only, no password);
2. controller key appended to `authorized_keys` (exact line, append-only);
3. sudo grant scope (managed file `/etc/sudoers.d/90-mai-<user>`);
4. connectivity — one scoped firewall rule (controller address + SSH port),
   never a blanket allow;
5. compose `.env` at `--env-file` (default `<repo>/.env`): created once,
   mode 0600, `MAI_POSTGRES_PASSWORD` (and `SEARXNG_SECRET` when `search`)
   generated in place, never echoed; an existing incomplete `.env` is a
   refusal, never merged;
6. stack start — `docker compose up -d --wait` with the selected profiles;
7. canonical pair — `mai.cli bootstrap --data-root … --server-id …` with the
   profile pointing at `--ssh-host` and the pinned host-key fingerprint.
   A rerun over an existing profile is refused (`stale_revision`) and the
   existing pair is preserved; deliberate re-provisioning is
   `mai admin write --expect-revision` (see `uninstall.md` §rotation).

Exit codes: `0` success/plan printed · `1` refusal or step failure · `2`
usage. The stack starts in **auth setup state**: no admin password exists
until you create it (§7); the installer generates none.

## 5. Verify the install

```bash
cd /path/to/repo/backend && uv sync --frozen
.venv/bin/python -m mai.cli status  --data-root /var/lib/mai
.venv/bin/python -m mai.cli doctor  --data-root /var/lib/mai --env-file /path/to/repo/.env
.venv/bin/python -m mai.cli status  --data-root /var/lib/mai --server-id <your-uuid>
docker compose --env-file ../.env ps
```

- `status` prints the read-only, value-free inventory (version triples
  revision/schema_revision/sha256 only).
- `doctor` re-checks permissions, hash/revision consistency, orphan
  metadata, symlinks and (with `--env-file`) the fail-closed `.env` source.
  It reports `hash_mismatch` etc. — it never repairs (recovery is
  `recovery.md`'s discipline).
- `docker compose ps` should show the core set (`postgres`, `mai-api`,
  `mai-web`) `healthy`. `mai-api` health is liveness-only
  (`GET /api/v1/health`); `GET /api/v1/health/ready` reports dependency
  readiness and is the one to check after a database outage.

`mai.cli` exit contract: `0` success, `1` structured rejection (one JSON
`{"error":{"code","message"}}` line on stderr), `2` usage/IO. Output is
value-free — no profile text, no credential values, ever.

## 6. Reach the browser (operator-supplied TLS proxy)

Nothing is reachable from the host network by default. Attach your TLS-
terminating reverse proxy to the `mai` Compose network and publish one
origin:

- route `/api/v1/*` to `mai-api:8000` and everything else to `mai-web:3000`
  (the web client calls the API same-origin);
- set `Host`, `X-Forwarded-Proto`, `X-Forwarded-For`; HTTP→HTTPS redirect;
  HSTS; pass bodies unparsed (auth ADR §6.4).

Then make the API trust the proxy and your origin — via a Compose override
that adds to the `mai-api` service environment:

| Variable | Meaning |
|---|---|
| `MAI_PUBLIC_ORIGINS` | Exact browser origins allowed to mutate, e.g. `https://mai.lan.example:8443`. No wildcards; invalid entries fail closed (every mutation then rejects) |
| `MAI_TRUSTED_PROXIES` | CIDR/name peers allowed to set forwarded headers (unset ⇒ forwarded headers ignored everywhere) |

Honest limits: this release ships no proxy service and no override file;
the env-var behavior above is the reviewed, tested auth surface
(`backend/tests/test_auth_http.py` — origin/CSRF/forwarded-header rules).
Plain-HTTP serving is allowed only on loopback (development). Public-internet
exposure is out of scope in v1; LAN and Tailscale are the intended access
paths (auth ADR §7).

## 7. One-shot admin bootstrap and login

Open your origin in the browser. In setup state only health and the one-shot
bootstrap are functional; every other route is refused `401`/`403`
fail-closed. Create the admin credential exactly once:

```bash
curl -fsS -X POST https://your.origin/api/v1/auth/bootstrap \
  -H 'Content-Type: application/json' -d '{"password": "<choose-in-browser-or-here>"}'
```

- The endpoint accepts `{ "password": "…" }` exactly once — afterwards it
  returns `409` permanently (no resurrection of setup state).
- Alternatively set `MAI_ADMIN_PASSWORD` or `MAI_ADMIN_PASSWORD_FILE` in the
  `mai-api` environment before first start; it is consumed once a credential
  record exists and never re-read.
- The credential is stored Argon2id-hashed in Postgres; the plaintext is
  never persisted or logged.

Log in through the UI (session cookie `mai_session` + CSRF token, server-side
revocation, wrong-password ≡ throttled latency). From here, enroll further
managed servers through the guided flow in the app: open **Enroll server**,
copy the displayed controller public key to the target's `authorized_keys`,
run the guided test, compare the offered fingerprint, trust it and enroll
(§2.1) — the quickstart host is already enrolled by step 7 of the installer.

## 8. Optional stack profiles

| Profile | Adds | Notes |
|---|---|---|
| `worker` | `mai-worker` — the ONLY full durable engine (launch recovery, the one queue, DBOS schedules) | Profile-gated on purpose: the API never launches jobs |
| `search` | `searxng` + `valkey` | Engine queries leave the host toward public upstream engines — deliberate opt-in; requires `SEARXNG_SECRET` in `.env` |
| `memory` | `hindsight` (+ one-time `hindsight-db-init` on the dedicated `hindsight` Postgres database) | Internal only (API 8888/UI 9999, no published port); LLM/embeddings configuration is a stack-owner decision — see `deploy/hindsight/README.md` |

Start them explicitly: `docker compose --profile worker up -d` (combine as
needed, or via `--stack-profiles` at install time). The core set always runs.

## 10. Troubleshooting

| Symptom | Meaning / fix |
|---|---|
| `--grant-scope` change refused on rerun | Rerun with `--reconcile-grants` (replaces only the installer-managed sudoers file) |
| `blanket controller address … refused` | Use a /8-or-narrower scoped address; blanket firewall rules are never written |
| `.env exists but lacks required credential variables` | Complete it manually — the installer never merges or overwrites credentials |
| `stale_revision` from `bootstrap` | The pair already exists; re-provision deliberately via `mai admin write --expect-revision` |
| Every mutation returns `403` | `MAI_PUBLIC_ORIGINS` unset/invalid ⇒ fail-closed allowlist; fix the origin list (§6) |
| `400 request_rejected` behind a proxy | Forwarded-Host disagrees with Host from a non-trusted peer; set `MAI_TRUSTED_PROXIES` (§6) |
| Discovery `docker` lane shows `permission_denied` (`unix:///var/run/docker.sock`) | The remote SSH user (`mai`) on the target host is not in the `docker` group; run `sudo usermod -aG docker mai` on the target host (§2.1) |

## Supported platforms and limitations (exact)

- Tested set: Linux x86_64 controller/targets (see `README.md` table);
  `ufw`/`firewalld` honored when active; systemd `docker.service` is the
  `narrow` grant surface.
- Not supported in v1: Windows/macOS targets, fleets, public-internet
  exposure, messenger delivery, bundled TLS proxy, in-app plugin installer
  (`docs/plugins/quickstart.md` documents the real mechanisms).
- Monitoring collectors and the notification inbox exist; alert delivery is
  configured-not-armed in this release.
